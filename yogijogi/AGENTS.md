# 요기조기 (YogiJogi) 프로젝트 안내

## 프로젝트 개요

요기조기는 캠퍼스 안에서 목적지를 찾고, 이동 경로 주변의 공간 상태와 필요한 정보를 확인하는 지도 기반 서비스다. 단순 길 안내에 그치지 않고 바퀴벌레 목격, 흡연 흔적, 공사·고장 등 이동이나 이용에 영향을 주는 정보를 위치와 시간에 연결해 안내한다.

핵심 가치는 **학생이 현재 교내 상황을 알고 경로를 고르거나 문제를 파악할 수 있게 하는 것**이다. 신고 건수를 보여주는 데서 끝내지 않고, 정보가 얼마나 최근인지와 처리 상태를 함께 표현한다.

공식 서비스 이름은 **요기조기 (YogiJogi)** 로 표기한다. 문서 후반의 `요기 (Yogi)`는 임시 별칭으로 취급하고, 별도 결정 전까지 앱 이름·화면 제목·문서 제목에 단독으로 쓰지 않는다. 이후 다른 학교나 건물 환경으로 확장할 수 있도록 특정 학교의 고정 문구·데이터와 서비스 공통 로직을 가능한 한 분리한다.

## 제품 원칙

- 위치 정보에는 반드시 기준 시각, 상태, 출처를 함께 표시한다. 제보 정보와 학교가 확인한 정보를 구분한다.
- 오래된 제보가 현재도 유효한 것처럼 보이지 않게 만료·숨김 규칙을 둔다.
- 지도에 모든 제보를 같은 강도의 빨간색으로 표시하지 않는다. 최근 제보, 반복 제보, 확인·처리 상태를 시각적으로 구분한다.
- 신고는 문제 구역을 파악하고 담당자 응답을 연결하기 위한 기능이다. 특정인을 공개적으로 지목하거나 비난하는 공간으로 만들지 않는다.
- 익명 제보를 제공하더라도 사진과 본문에 이름, 얼굴, 차량 번호 등 개인정보가 포함될 수 있음을 고려한다. 공개 전 안내와 삭제·가림 처리를 고려한다.
- 시설팀에 실제로 전달되지 않는 프로토타입이라면 전달된 것처럼 표시하지 않는다. 발표용 시연은 가상 담당자 계정 또는 명시적인 데모 상태로 처리한다.
- 실시간 연동이 없는 정보는 실시간이라고 표현하지 않는다. 시간표, 행사, 시설 상태는 마지막 갱신 시각을 표시한다.
- 우선 핵심 경로 탐색과 공간 상태 확인을 구현한다. 모든 기능을 한 번에 완성하려고 범위를 키우지 않는다.

## 주요 기능

### 1. 캠퍼스 길찾기

- 건물·층·강의실 등 목적지를 검색하거나 지도에서 선택한다.
- 이동 옵션은 `최단거리`, `엘리베이터 우선`, `계단 없는 경로`로 구분한다.
  - 최단거리: 계단·엘리베이터를 모두 고려해 거리가 가장 짧은 경로
  - 엘리베이터 우선: 엘리베이터를 우선 이용하되 필요하면 계단 구간이 포함될 수 있는 경로
  - 계단 없는 경로: 계단을 제외하고 엘리베이터·경사로 등 접근 가능한 연결만 이용하는 경로
- 각 옵션의 차이를 화면에서 설명한다. 조건을 만족하는 경로가 없으면 다른 경로를 조용히 대체 표시하지 말고 경로가 없음을 알린다.
- 경로 주변에 최근 제보된 불편 정보를 표시한다.
- 엘리베이터 고장, 공사, 통행 제한 등 확인된 이동 제약이 있으면 경로 계산에서 제외하거나 우회 경로를 제안한다.
- 혼잡도는 신뢰할 수 있는 데이터가 없으면 표시하지 않는다. 혼잡도를 받지 않는 상태에서 정밀한 실시간 안내를 약속하지 않는다.
- 접근 가능한 실내 지도나 경로 데이터가 확보되지 않았다면 시연 범위를 정한 건물·층으로 한정하고, 샘플 경로임을 표시한다.

### 2. 지도 기반 공간 상태 제보

- 바퀴벌레 목격이나 흡연 흔적, 공사·고장 등 문제 유형과 위치를 제보한다.
- 한 지점에 여러 건의 제보가 쌓이면 반복 발생 구역으로 강조할 수 있다. 단, 건물·구역 단위로 표시하고 정확한 개인 위치를 노출하지 않는다.
- 제보 시각이 최근인 정보와 반복 제보를 구분한다. 담당자 확인·조치 상태가 바뀌면 지도 표시도 갱신한다.
- 시간 경과에 따라 표시를 약하게 하거나 자동 만료한다. 처리 완료된 정보는 진행 중인 제보와 다른 표시로 바꾼다.
- 바퀴벌레 제보는 방역 우선순위를 파악하도록 돕는 정보로 다룬다. 제보만으로 실제 방역이 진행됐다고 단정하지 않는다.
- 흡연 제보는 장소·시간대별 반복 구역 파악과 시설 대응을 돕는 데 초점을 둔다. 흡연자로 추정되는 개인의 사진·신상 공개나 공개 비난을 유도하지 않는다.

### 3. 장소 행사 안내

- 행사 장소를 지도에 표시하고, 카드에서 제목·주최자·기간·시간·장소 등 기본 정보를 확인할 수 있게 한다.
- 게시 기간이 끝난 행사는 기본 목록과 지도에서 내린다.
- 홍보 게시물이 쌓여 길찾기 화면을 가리지 않게 지도 표시와 행사 목록을 분리하거나 필터로 제어한다.
- 초기에는 승인된 샘플·운영자 등록 행사만 노출해도 된다. 동아리·행사 주최자의 직접 등록 기능은 등록 양식, 검토 주체, 종료 처리가 정해진 뒤 확장한다.

### 4. 강의실 정보

- 강의실을 선택하면 해당 시간대의 수업 정보를 보여준다.
- 시간표가 실제 연동되지 않으면 정적 샘플 데이터임을 표시하고 마지막 갱신 시각을 제공한다.
- 수강생 개인 정보나 출석 여부는 노출하지 않는다.
- 시간표를 기준으로 안내할 때는 현재 수업 중, 다음 수업 예정 등 표현과 시간대를 명확히 한다. 실제 강의 변경·휴강이 반영되지 않을 수 있음을 고려한다.
- `이용 가능`은 실시간 점유 센서가 없는 한 시간표상 수업이 없는 상태를 뜻한다고 명시한다. 실제로 비어 있다고 보장하지 않는다.

### 5. 흡연·시설 문제 신고와 답변

- 게시글은 익명 또는 닉네임 표시를 선택할 수 있다. 담당자 답변을 위한 연락처는 공개 게시글과 분리하고, 연락처 입력은 필요한 경우에만 선택적으로 받는다.
- 위치, 문제 유형, 설명, 발생 시각, 선택 사진을 입력한다.
- 처리 상태는 예를 들어 `접수`, `확인 중`, `조치 중`, `완료`로 구분한다.
- 담당자 답변과 상태 변경 시각을 게시글에 남긴다.
- 사진 업로드 전 개인정보 노출 가능성을 안내한다. 신고 사진은 문제 확인에 필요한 범위로 제한하고, 공개 범위와 보관 기간을 고려한다.
- 실제 담당 부서와 연동되기 전에는 제보가 학교에 접수됐다고 사용자에게 오해시키지 않는다.

### 6. 제보 둘러보기 및 공감

- 바퀴벌레, 흡연, 시설 고장 등 카테고리와 처리 상태로 제보 목록을 필터링할 수 있다.
- 제보 카드에는 위치, 제보 시각, 출처, 처리 상태를 우선 표시한다.
- `나도 봤어요` 같은 공감은 추가 목격 신호로만 취급한다. 공감 수만으로 제보가 사실로 확인되었다고 표시하지 않는다.
- 행사 목록은 불편 제보 목록과 구분해 탐색할 수 있게 한다.

## 화면·UX 지침

- 지도 중심(Map-first)의 모바일 UI를 기본으로 한다. 검색, 필터, 장소 정보는 지도 조작을 막지 않는 상단 검색창·하단 내비게이션·바텀시트 등으로 구성한다.
- 지도에는 모든 정보 레이어를 한꺼번에 강하게 노출하지 않는다. 경로, 장소, 행사, 제보를 아이콘·필터로 구분하고 사용자가 필요한 레이어를 선택할 수 있게 한다.
- 화면을 설계하거나 생성형 디자인 도구에 요청할 때는 공통 서비스 맥락을 유지하면서, 매 화면마다 `사용자`, `화면 목표`, `화면 유형`, `필수 정보`, `주요 행동`, `제약 조건`을 구체적으로 지정한다.
- 친근하고 귀여우면서 깔끔하고 현대적인 분위기를 지향한다. 둥근 카드·버튼과 부드러운 색을 사용할 수 있지만 지나치게 유아적이거나 장식이 정보를 가리는 디자인은 피한다.
- 바퀴벌레 아이콘은 징그럽거나 위협적으로 표현하지 않고, 단순하고 식별 가능한 형태로 표현한다.
- 학생 제보와 담당자가 확인한 정보는 색상만으로 구분하지 말고 라벨·아이콘·상태 텍스트도 함께 사용한다.
- 글자 크기, 터치 영역, 색 대비를 충분히 확보하고 한 손 조작과 화면 읽기 흐름을 고려한다.

## 하루 안에 시연 가능한 MVP 범위

실제 교내 시스템 연동이나 자동 방역 요청은 필수 범위로 잡지 않는다. 발표 가능한 흐름을 먼저 완성한다.

1. 샘플 캠퍼스 지도에서 건물·강의실 선택
2. 미리 준비한 경로 데이터로 최단거리·엘리베이터 우선·계단 없는 경로 전환
3. 지도 위에 샘플 제보 핀 표시 및 유형·시각·상태 확인
4. 제보 등록 폼에서 위치·유형·설명 입력 후 목록 또는 지도에 반영
5. 강의실 시간표와 행사 정보를 샘플 데이터로 표시
6. 신고 상세에서 가상 담당자 답변과 처리 상태 표시

우선순위가 밀리면 행사·시간표의 실시간 연동, 사진 업로드, 자동 경로 재계산, 외부 행사 주최자 등록을 제외하고 핵심인 **길찾기 + 경로 주변 상태 표시**를 남긴다.

## 브랜치 규칙

- `main`은 항상 팀이 확인할 수 있는 안정 버전으로 유지한다.
- 기능은 작업별 브랜치에서 개발하고 PR(Pull Request)로 `main`에 병합한다.
- 기능 브랜치는 아래 형식을 사용한다.
  - `feature/navi#1` — 네비게이션 기능
  - `feature/complain#1` — 신고 기능
  - `feature/place#1` — 장소·공간 기능
- 구조 개선 브랜치는 다음 형식을 사용한다.
  - `refactor/navi#1` — 네비게이션 코드 구조 개선
- `navi`, `complain`, `place`는 작업 영역을 나타내고, `#1`은 해당 작업 번호나 이슈 번호로 사용한다. 팀 내 번호 사용 방식을 일관되게 유지한다.
- 작은 수정이라도 다른 팀원의 작업과 충돌할 수 있거나 기능 동작에 영향을 주면 브랜치를 만들고 PR을 올린다.

## 커밋 규칙

- 커밋 메시지는 `[유형] 변경 내용` 형식으로 작성한다.
- 유형은 우선 `[feat]`를 사용한다. 기능 수정·추가를 설명하는 짧고 구체적인 문구를 뒤에 적는다.
- 예시:
  - `[feat] 엘리베이터 우선 경로 선택 추가`
  - `[feat] 바퀴벌레 제보 핀 표시`
  - `[feat] 신고 상세에 담당자 답변 표시`
- 한 커밋에는 가능한 한 하나의 목적에 해당하는 변경만 담는다.

## PR 및 병합 규칙

- PR을 만들 때 변경한 기능, 확인 방법, 남은 작업이나 주의점을 적는다.
- PR 생성 시 리뷰어를 지정한다.
- 리뷰를 받기 전에는 `main`에 병합하지 않는다.
- 리뷰어는 기능 동작, 화면·데이터 흐름, 개인정보 노출 여부를 확인한다.
- 리뷰에서 수정 요청이 있으면 반영한 뒤 다시 확인을 요청한다.
- 승인된 PR만 `main`에 병합한다.

## 코드 작업 시 지침

- 작업 전에 현재 브랜치와 변경 파일을 확인하고, 팀원의 미커밋 변경을 덮어쓰지 않는다.
- 기존 프로젝트 구조와 사용 중인 기술 스택을 먼저 확인한다. 이 문서만으로 프레임워크나 백엔드가 확정된 것으로 가정하지 않는다.
- 새 패키지나 외부 API를 추가하기 전에 기존 의존성과 구현 방식을 확인한다.
- 지도에 보이는 제보는 유형, 위치, 발생 시각, 처리 상태를 데이터 모델에서 구분해 관리한다.
- 실제 정보와 데모 데이터를 화면과 코드에서 구분한다.
- 변경 후에는 영향받은 기능을 직접 확인하고, 확인하지 못한 항목은 PR에 적는다.
